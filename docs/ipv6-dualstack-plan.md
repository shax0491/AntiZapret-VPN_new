# План внедрения IPv6 (Dual-Stack) для AntiZapret и VLESS

Дата замеров: 03.11.2026. Раздел «Факты» получен на живых узлах и роутере, остальное - план. Строки, помеченные **(проверить)**, не проверялись на нашем железе.

Что нужно от вас: для DE2 и DE4 в панели хостера посмотреть выданные адрес, префикс и шлюз IPv6. Пока их нет, на серверах делать нечего: ни RA, ни DHCPv6 хостер не присылает.

## 2. Главный риск: 2001:2::/48

`2001:2::/48` (RFC 5180, диапазон для тестов) форк Nessusd берёт как «фиктивную» сеть для AntiZapret. Keenetic уже использует тот же диапазон на `ezcfg0`. Если роутер увидит клиентский адрес из `2001:2::/48`, возможен конфликт маршрутов. Поэтому:

- на узлах диапазон брать можно (там он локален внутри туннеля);
- на Keenetic **не** маршрутизировать `2001:2::/48` в LAN и не вешать его на LAN-интерфейсы; клиенту AntiZapret на роутере давать только ULA;
- запасной вариант без риска - `ALTERNATIVE_FAKE_IPV6=n` (фиктивные адреса из ULA `/96`, как предусмотрено форком).

## 3. Что берём из форка и что нет

Берём:
- ULA `/96` для клиентов VPN (`VPN_IPV6_PREFIX`), NAT66 через `ip6tables`/`nft`, v6-наборы для списков;
- AAAA-ответы для доменов AntiZapret через туннель, `NOERROR/NODATA` для типов без записи;
- dual-stack профили WireGuard/AmneziaWG, `::/0` в `AllowedIPs` у Full VPN.

Не берём (лишнее для нас): BGP/BIRD, OpenVPN DCO, раздачу маршрутизируемых префиксов роутерам (экспериментально, `/48`-`/64`). Причина: у нас клиенты - WG/AWG и VLESS, а Keenetic не умеет принимать префикс из туннеля.

Наша база проще форка: на каждом узле одна nft-таблица `inet antizapret6` вместо россыпи ip6tables-цепочек (на узлах уже есть `table ip antizapret`, схема та же).

## 4. План по узлам (порядок: NL2, затем DE2/DE4)

Шаг 0. Только после получения адресов от хостера (DE2/DE4).

1. Адрес и шлюз. В `/etc/netplan/50-cloud-init.yaml` (под `ens3`) добавить статикой v6-адрес и `routes: - to: ::/0, via: <шлюз>`; выставить `accept-ra: false`, чтобы не зависеть от RA. `netplan try`, не `apply` - откат сам при потере связи. Проверка: `curl -6 https://ifconfig.co/ip` показывает адрес узла.
2. sysctl. Заменить `99-disable-ipv6.conf`: `all/default.disable_ipv6=0`, `net.ipv6.conf.all.forwarding=1`, а для основного интерфейса `accept_ra=2` не нужен (адрес статический).
3. Настройки AntiZapret: `DISABLE_IPV6=n`, `ALTERNATIVE_FAKE_IPV6=y`; применить перезапуском `antizapret`.
4. NAT66 и фиктивные адреса (аналог текущего nft):
   ```
   nft add table ip6 antizapret6
   nft add chain ip6 antizapret6 postrouting '{ type nat hook postrouting priority 100 ; }'
   nft add rule  ip6 antizapret6 postrouting ip6 saddr fd00:28::/96 oifname "<внешний>" masquerade
   nft add map ip6 antizapret6 mapping '{ type ipv6_addr : ipv6_addr ; }'
   nft add chain ip6 antizapret6 mapping_hook '{ type nat hook prerouting priority -50 ; }'
   nft add rule  ip6 antizapret6 mapping_hook ip6 saddr fd00:28::/96 ip6 daddr 2001:2::/48 dnat to ip6 daddr map @mapping
   ```
   (`fd00:28::/96` - пример ULA; брать реальный из `VPN_IPV6_PREFIX`.) Заполнять `mapping` из `proxy.py` по образцу IPv4-карты **(проверить: proxy.py сейчас пишет только ipv4_addr)**.
5. Брандмауэр: разрешить forward для ULA-сети клиентов и `ct state established,related`; обязательно запретить forward v6 между клиентами (изоляция, как в IPv4).
6. DNS: в `kresd` включить выдачу AAAA для клиентов dual-stack; AAAA для имён, которые на этом узле идут через Proton, **подавлять** (отвечать NODATA), иначе клиент уйдёт по v6 мимо Proton и выдаст реальный адрес узла.
7. Проверка на netns-клиенте: `curl -6` на сайт из списка и на обычный; `curl -4` как раньше; AAAA-запрос на имя из списка даёт адрес из `2001:2::/48`.

## 5. VLESS (xray)

1. Inbound слушает `::` (dual-stack): `"listen": "::"`; порт 8443/8445 открыть и в `ip6tables`/ufw.
2. DNS Cloudflare: добавить AAAA для `de2`, `de4`, `nl1` (DNS-only, без прокси). Это позволяет клиенту подключаться к узлу по IPv6 и обходить блокировки отдельных v4-адресов. Для узлов без v6 AAAA не добавлять.
3. Outbound `direct`: `domainStrategy: "UseIPv4v6"` на NL2 (v6 есть); на узлах без v6 оставить `UseIPv4`. Outbound `proton` (привязан к интерфейсу `proton`): строго `UseIPv4`, так как туннель Proton IPv4-only.
4. Mihomo на роутерах: `ipv6: true` в корне и в `dns:`; в `az-vless` провайдере подписка уже отдаёт хосты, ничего менять не нужно. Включать только когда у узла есть AAAA.

## 6. Keenetic (основной)

Исходная ситуация: провайдер IPv6 не даёт, значит дом остаётся IPv4, а v6 появляется только на участке «роутер - узел» и внутри туннеля.

Этап 1 (рекомендую, минимум изменений):
1. LAN остаётся IPv4. Mihomo на роутере ходит на узлы по IPv6 (если у узла есть AAAA) и использует v6 outbound на NL2. Клиентам ничего не раздаём, DHCPv6/RA не нужны.
2. Если нужно, чтобы клиенты видели v6-сайты: Mihomo с `dns.ipv6: true` и TUN/redirect сам отдаёт клиентам A-записи, а v6-назначение берёт на себя.

Этап 2 (по желанию, когда на узлах всё стабильно):
1. В «Параметрах системы - Изменение набора компонентов» убедиться, что компонент **IPv6** установлен **(проверить)**.
2. AWG-интерфейс к узлу: `Address = <v4>, fd00:28::<n>/128`, `AllowedIPs = 0.0.0.0/0, ::/0` в Full VPN профиле. Для AntiZapret-профиля: `AllowedIPs` только нужные v4-подсети и `2001:2::/48` не использовать (см. раздел 2), вместо него ULA `/96`.
3. RA/DHCPv6 в LAN (Bridge0): раздавать ULA `fd00:LAN::/64` (SLAAC, режим `slaac`; DHCPv6 только если нужен DNS) **(проверить синтаксис `ipv6 subnet Default` / `bind` / `mode slaac` на 5.2 Beta 2 в CLI Keenetic)**.
4. Маршрут по умолчанию v6 через AWG-интерфейс в нужной политике доступа (`ipv6 route ::/0 <интерфейс>`).
5. Ограничение: NAT66 на Keenetic не поддерживается, поэтому ULA клиенты LAN в интернет сами не выйдут; NAT66 выполняет узел. Поэтому весь v6 LAN-трафика должен идти в туннель, а утечка по v6 «в обход» исключается правилом запрета forward v6 не через туннель **(проверить: на Keenetic нет `ip6tables` из LAN, использовать политики доступа и `no ipv6 ...`)**.
6. Откат: удалить `ipv6 subnet`, убрать `::/0` из `AllowedIPs`.

## 7. Cudy OpenWrt (вторичный)

1. `network.lan.ip6assign=64`, `network.globals.ula_prefix=fdXX:XXXX:XXXX::/48`; `dhcp.lan.ra=server`, `dhcp.lan.dhcpv6=server`, `ra_flags=other-config`.
2. Туннель WireGuard к узлу: адрес `fd00:28::<n>/128`, пир с `allowed_ips='::/0'` (+ v4), `route_allowed_ips=1`.
3. NAT66 прямо на роутере (в OpenWrt поддерживается): `firewall.zone` для туннеля `masq6=1` (нужен пакет `kmod-nft-nat` / `ip6tables-mod-nat`) **(проверить на TR3000)**; тогда LAN-клиенты с ULA выходят в интернет через узел без участия узла в NAT66.
4. MTU туннеля 1280 для надёжности; MSS clamp включён.
5. Политика узла: основной - DE2 (как для IPv4-пути), запасной - NL2 (единственный с рабочим v6 сегодня). До появления v6 на DE2/DE4 запасной путь NL2 - единственно рабочий.

## 8. Порядок внедрения и откат

1. NL2: пункты 4 и 5 раздела 4 как пилот; Mihomo-клиент через `curl -6`.
2. DE2/DE4: после выдачи адресов хостером, тот же сценарий.
3. DNS AAAA для узлов - в самом конце, по одному узлу.
4. Откат на узле: `DISABLE_IPV6=y`, вернуть `99-disable-ipv6.conf`, `nft delete table ip6 antizapret6`, убрать AAAA из Cloudflare. Бэкапы файлов перед правкой в `/root/bak-ipv6-<дата>`.

## 9. Что не проверено

- Работоспособность ни одного шага раздела 4-7 на живой инфраструктуре (это план).
- Поведение `proxy.py` с v6-картой и `warp_hook` для v6.
- Команды Keenetic CLI и пакеты OpenWrt помечены **(проверить)**.
- Утечка по IPv6 мимо Proton: исключается только подавлением AAAA и запретом forward v6 вне туннеля, оба пункта требуют отдельного теста до включения.
